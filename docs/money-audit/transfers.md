## Findings and proposed review rules

| ID | Confidence | Evidence | Suggested review rule | Decision needed |
| --- | --- | --- | --- | --- |
| TR-01 | High, code behavior; unknown row incidence | `money-repository.ts` `collectDateTransferPairs` and `collectMutuallyUnique` pair opposite amounts in different accounts within three calendar days when each side has one candidate. They do not compare provider, counterparty, description, account ownership, or a bank reference. | Flag every automatically linked pair for which account ownership or counterparty evidence is absent; preview both rows and the full nearby candidate set. Keep auto-linking limited to pairs with corroborating identity or source reference. | Review all existing `transfer_group_id` pairs before assuming they represent owned-account movements. |
| TR-02 | High, code behavior; unknown row incidence | `money-transfer-inference.ts` gives certain provider/source/description combinations `internal_transfer` even without a paired opposite ledger row. Examples include portfolio `CUSTOMER_INBOUND`, Revolut `CASH TOP-UP`, and Sparkasse `HOMEBANKINGUEBERWEISUNG`. | Treat inferred unpaired transfers as an explicit **unmatched internal transfer** review state. Seek the corresponding account, date, amount, and source evidence; keep a one-sided movement only when an external owned account is intentionally outside the ledger. | Approve each owned-account mapping and any justified one-sided transfer. |
| TR-03 | High, code behavior; unknown row incidence | `money-repository.ts` `reimportAll` clears linked groups and transfer dispositions on imported rows and reruns the inference. | Before reimport, preview dispositions and links that would change. Preserve manual decisions or explicitly request reapproval for them. | Confirm whether a reimport is allowed to replace prior manual transfer review. |
| TR-04 | Medium, possible misclassification | `money-transfer-inference.ts` treats Revolut `Transfer` positive amounts without a recognized owned-account description as `refund`; negative amounts as `spend`. Incoming third-party payments can be income, gifts, reimbursements, refunds, or loans. | For positive external transfers, propose `income` or `refund` only from counterparty and history evidence. Group recurring counterparties but require row preview; do not infer income solely from positive sign. | Classify each counterparty and exceptions. |
| TR-05 | Medium, possible misclassification | `money-transfer-inference.ts` classifies Sparkasse positive `HOMEBANKINGUEBERWEISUNG` as internal transfer, unless an earlier income pattern matches. The classifier in `money-import-domain.ts` initially treats positive transfer types as `transfer`. | For positive Sparkasse bank transfers, require evidence that sender is an owned account before `internal_transfer`; otherwise review as income/refund/gift or other inflow. | Check actual sender fields for every matching row. |
| TR-06 | High, data model constraint; unknown row incidence | Imported transaction `account_id` is derived from source account references in `money-import-domain.ts` and inserted through `money-repository.ts`. There is no account reassignment rule or preview path in the inspected model. | Validate account assignment against original import account identifier and provider account metadata. Propose reassignment only when source evidence conflicts; preserve provenance. | Decide misassigned rows after source comparison. |

## Historical ledger checks to run once a safe source is available

1. Inventory every account by `id`, provider, external reference, role, and currency; compare with import account identifiers. Record last transaction and balance observation separately.
2. Export all effective transactions and raw reverted rows with transaction ID, import ID, source key, date, account ID, amount/currency, source type, description, flow, category, disposition, and transfer group. Reconcile count and date range against database totals.
3. For each transfer group, verify exactly two effective rows, different owned accounts, equal and opposite currency amounts, plausible dates, and corroborating counterparty/source evidence. List any mismatches by row ID.
4. For each unpaired row marked `internal_transfer`, search all owned accounts for a matching opposing row. Distinguish missing imports from legitimate off-ledger owned accounts.
5. For every transfer classified `income`, `refund`, `spend`, or `excluded`, inspect source evidence and recurring counterparties. Check sign, category, and cash-flow treatment; list exceptions by row ID.
6. Search **all** effective flows, including `spend`, `refund`, and `income`, for owned-account funding descriptions. A zero unresolved-transfer count only covers transfer rows without a group or disposition.

Each eventual proposal should record current and proposed account, flow, category, disposition, group, supporting row IDs, amount/date, reason, confidence, and an individual approval status. Approval should be separate from rule creation, and rule preview should show every historical row it would affect.
